Build and release

Local verification

Use JDK 17, Android platform 36 and build tools 35.0.0. Set ANDROID_HOME or untracked local.properties with sdk.dir=/path/to/sdk. The pinned wrapper verifies its download checksum.

./gradlew testDebugUnitTest lintDebug assembleDebug assembleRelease
./gradlew connectedDebugAndroidTest  # emulator or connected device

Installable development APK: app/build/outputs/apk/debug/app-debug.apk. The production release variant is unsigned. Test-only synthetic audio/document-provider fixtures never ship in the app.

Verify affected contracts: migrations/recovery and failed operations. Occurrence/cursor/metadata preservation. Navigation/search restoration and gesture ownership. Playback/lyrics/artwork boundaries. Accessibility, short/landscape screens, large fonts and reduced motion. Physical-device review supplements automation. Docs-only edits require content/link review, not Android tests.

Local and CI verification use the same tests and Gradle launcher. Use focused tests during iteration, then run the complete build/check commands and connectedDebugAndroidTest on both API 26 and 36 against the final candidate before pushing. Match the emulator configuration below. Code, test or build-configuration changes after that gate require another full run.

CI repeats verification in a fresh environment on the pushed commit before release.

A workflow dispatch may supply risk_classes as up to 20 comma-separated fully qualified instrumentation classes (4096 characters maximum). The hosted disposable device job records that selector and runs it before the unchanged complete suite.

A failed preflight stops the job and preserves its exit status, log and reports. A passing preflight resets only the app/test packages before running the full suite. Focused success alone is never release evidence. Empty input and ordinary PR/main runs retain full-suite behavior.

Preflight isolation is not used by the compatibility gate, whose app data must persist across phases.

Documentation

Use Node.js 22 or newer. From a fresh clone, install only the documentation tooling:

git clone https://github.com/anastaci1a/localica.git
cd localica
npm ci --prefix tools/docs --ignore-scripts
npm test --prefix tools/docs
npm run check --prefix tools/docs
npm run build --prefix tools/docs

Open build/docs-site/docs/index.html to review the site locally. No Android SDK, signing key or device is needed for these checks. Mathematical display blocks render to HTML and MathML during the build. Fonts and styles are local assets.

The documentation workflow checks pull requests and publishes main to the existing gh-pages branch. It replaces only the docs/ directory, preserving all other deployed files.

The site lives at Localica documentation. Maintained-document links resolve to rendered pages. Source and historical links remain explicit GitHub links. No hosting settings or release tags change.

Writing rules define the maintained inventory and historical exclusions. Automated checks cover prose limits, local links and fragments, headings, image descriptions and rendered navigation. Review contract meaning and remote evidence separately.

Compatibility and dependencies

Queue schema 7 cannot be reopened by the original schema-6 APK. Before distributing it, dispatch the exact candidate through the Android workflow with compatibility=true. Its API 26/36 gate installs candidate → legacy-behavior bridge → candidate with the same package/signature and increasing private version codes, without clearing data.

The isolated overlay retains current schema, journal and recovery safety. Only traversal behavior changes. ShuffleApkCompatibilityTest checks duplicate occurrences, saved order/cursor, controller reopening and statistics across seed, bridge, then verify. Bridge journal/recovery checks run separately. Private compatibility artifacts are never distributed: use the canonical localica-debug APK. Ordinary migration tests do not replace this gate.

Track exact-source evidence in #295.

Finish tag editing, recovery and pending metadata refreshes before downgrading: older builds cannot read the incremental metadata-refresh records. The existing array journal migrates on upgrade. Queue database schemas are independent.

Android 8+; MP3 and AAC/M4A are primary formats, with WAV/FLAC/Ogg/Opus using available device decoders. No decoder extensions. Boundary tests check decoded samples, MP3 waveform alignment and transition buffering. Sample counts alone are insufficient.

FLAC tests require a decoder (stock Android supplies one from API 27). Known padding limits: some shortened-final-sample FFmpeg M4A files (#28) and the legacy Android 8 MP3 decoder (#30). Only the precise known Android 8 failure is skipped after playback checks. Other failures remain failures.

Media3 stays pinned to 1.10.1 pending a stable MP3 trimming fix. Rerun waveform checks before upgrading.

Jaudiotagger 3.0.1 uses LGPL 2.1+. Bundle its notice/license and include its source archive with releases. To replace it, build the source with Maven, replace implementation(libs.jaudiotagger) with the local JAR, and rebuild under your signing key. Localica remains MIT licensed.

CI and signing

The Android workflow builds application changes on main/PRs and tests API 26/36. Documentation-only changes use the separate documentation workflow. API 36 uses explicit lavapipe, 720×1280 at 280 dpi, and normal system animations: automatic software/SwiftShader caused rendering crashes. Zero-duration system transitions stalled launcher/Back/picker flows. Compose assertions control their own clock. Keep Actions pinned by commit.

ANDROID_DEBUG_KEYSTORE holds the base64 development key; CI restores it via LOCALICA_DEBUG_KEYSTORE and verifies the APK certificate. Back up the key outside Git. Local builds otherwise use the normal debug key; PRs use a disposable key. Regular GitHub releases retain the existing .debug application ID and development key for in-place updates. Separate production signing is not configured.

Release preparation

Prepare the candidate

Update app version/name and increment versionCode for every distributed update. Fill the template into RELEASE_NOTES: basic APK/compatibility/signing introduction, short Changes bullets, all resolved issue URLs with brief description fragments, and short Install steps. Include only completed issues. Say so if none. Keep previous published descriptions intact.

Review previews, current docs and resolved issues. Commit and push.

Verify the exact commit

Wait for successful build, both device jobs, and both compatibility jobs on the exact main SHA before tagging it. The matching vX.X.X workflow reuses that run's APK, verifies version/signature/checksum, and publishes without another build/test matrix. Missing verification/expired artifacts require rerunning main checks. Never substitute another commit's APK. Unfilled release placeholders block publication.

Verify publication

Verify published assets, close resolved issues/remove workflow labels, and replace completed roadmap outcomes with the next checkpoint.

Previews

Review README screenshots/GIF for each release. Recapture changed screens from the candidate, inspect at README size, update version/credits and remove obsolete images. Keep navigation recordings short/silent and third-party demo media outside Git/APK.

Reuse ${XDG_DATA_HOME:-$HOME/.local/share}/localica/previews/ for the local library, setup notes and raw captures. Preserve emulator music/app data. Update with adb install -r rather than recreating the library.
